How the screener works

A recruiter drops a job description and forty resumes. Three AI calls later there is a ranked shortlist and a set of interview questions. Everything else in this codebase is plumbing around those three calls.

01The three calls

Strip away the routing, the file handling and the React, and the whole product is three prompts sent to a language model.

CallRuns whenPromptReturns
Parse a role Once per job description, while you wait extract_jd.md Title, must-have and good-to-have skills, years, responsibilities
Screen a candidate Once per resume, in the background screen_resume.md Name, email, phone, total and relevant years, per-skill scores, rating, reason
Write the tech round On demand, per candidate generate_questions.md Questions tagged by skill and difficulty, with expected answers
Why one call per resume, not two

The obvious split is "extract the profile, then score it". This does both at once, because the model needs the full resume in context either way — and the free tier meters you per call. Merging them halves the cost and doubles the throughput.

02The request fork

The single most important thing to understand: when you upload forty resumes, the HTTP response comes back before any AI work has started.

If screening ran inside the request, the browser would hang for eight minutes. Instead the route does only the fast work — save the files, write forty PENDING rows, reply — and hands the slow work to a background task. The route never talks to Gemini.

03Every file's job

Thirteen backend files, eleven frontend files. Each has one job, and the layering rule keeps them honest.

Routers handle HTTP — status codes, 404s, saving uploads. Services handle logic and never import FastAPI. llm.py handles the AI. A router never calls Gemini; a service never raises an HTTP error.

05Structured output

There is no JSON parsing anywhere in this codebase. You hand the model a Pydantic class and get an object back. 

# schemas.py — you describe the shape you want
class LLMScreening(BaseModel):
    name:  str | None = Field(None, description="Candidate's full name")
    email: str | None = Field(None, description="Email address")
    score: int        = Field(ge=0, le=100,
                              description="Overall match rating, 0-100")
    reason: str       = Field(description="2-3 sentences justifying the score")

# llm.py — the entire AI interface, one function
def ask(prompt: str, schema: type[T]) -> T:
    return get_model().with_structured_output(schema).invoke(prompt)

# services.py — how you call it
result = ask(prompt, LLMScreening)
result.score   # an int, guaranteed 0-100
result.email   # a str or None

Three things come free with that:

  1. The description= text is sent to the model as part of the instruction. Those descriptions are prompt engineering, not documentation.
  2. ge=0, le=100 is enforced. A model that returns 150 raises, and the resume is marked FAILED rather than storing nonsense.
  3. You get an object, not a string. No json.loads, no stripping of stray code fences.

Swapping Gemini for GPT

llm.py is the only file that imports a provider, so a swap is two lines in .env: 

LLM_PROVIDER=openai
LLM_MODEL=gpt-4o-mini
OPENAI_API_KEY=sk-...

This is what LangChain is here for. Both provider classes implement the same BaseChatModel interface, so .with_structured_output(schema).invoke(prompt) behaves identically on either. That is the whole benefit — and it is worth the dependency.

The rate limiter

The Gemini free tier allows five requests a minute. Without pacing, four screening threads fire at once, three get a 429, and everything backs off. An InMemoryRateLimiter is attached to the model itself, so it covers every call path and is shared across all threads. Raise LLM_RPM_CAP on a paid key.

06The prompts

They live in backend/prompts/ as plain markdown, not Python strings. You can change the AI's behaviour without touching code.

Placeholders use {{double_braces}} and are filled by load_prompt(). Two instructions in screen_resume.md are doing most of the work.

Relevant experience, not just total

"…only the portion of that experience which involved this role's must-have skills. This is normally LESS than total experience. A backend engineer of 8 years applying for a frontend role may have only 2 relevant years. Be strict."

In a live test a frontend engineer with a genuine five years came back as 5.0 total, 0.0 relevant against a backend payments role. That one field is the difference between a list of resumes and an actual shortlist.

A rubric, not a vibe

Without explicit anchors, models cluster every candidate around 70.

ScoreWhat it means
0No mention at all
1–3Listed in a skills section only, no supporting work described
4–6Used in real work, described briefly
7–8Clear repeated hands-on delivery, with specifics
9–10Deep expertise: led, architected or scaled work with this skill

Fit is computed, never asked for

The model returns a score out of 100. The BEST MEDIUM NO label is worked out in Python from thresholds in .env: 

def fit_for(score: int) -> str:
    if score >= settings.FIT_BEST_MIN:    # 75
        return Fit.BEST
    if score >= settings.FIT_MEDIUM_MIN:  # 45
        return Fit.MEDIUM
    return Fit.NO

So you can retune the cutoffs and every future screening obeys them instantly — no prompt edit, no risk of the model drifting, and the thresholds sit in one visible place instead of buried in English.

07When things fail

The rule throughout: a failure is data, not an exception. One bad file must never break a batch of forty. 

# services.py
def screen_resume(resume, jd) -> None:
    resume.status = Status.PROCESSING
    try:
        ...
        resume.status = Status.DONE
    except UnreadableFile as exc:
        resume.status, resume.error = Status.FAILED, str(exc)
    except Exception as exc:
        resume.status, resume.error = Status.FAILED, f"Could not screen this resume: {exc}"

It returns None and never raises. The failure is written onto the row, so it surfaces in the table as a FAILED badge with the reason and a Retry button — and the other thirty-nine carry on.

Caught whereWhat it catchesWhat you see
UploadUnsupported file typeMarked failed at once — no AI call wasted
files.pyCorrupt file, scanned PDF with no text layer"No text found in cv.pdf…"
services.pyAI call failed, quota exhausted"Could not screen this resume: …"
Worker threadA thread crashing outrightLogged; the rest of the batch continues

The one deliberate exception is assessment generation, which does raise and becomes a 502. You are sitting there waiting for that one, so an error on screen beats a silently empty panel.

08Why there is no vector database

The instinct on an "AI + documents" project is Chroma and embeddings. It was built, then deliberately removed. Here is the reasoning, because it is the decision most likely to get re-litigated.

Retrieval exists to solve exactly one problem: source text too big for the context window. Chunk it, embed it, retrieve only the relevant pieces. That is a real problem — just not this one.

When it would earn its place

Searching across the candidate pool — "who has done Kafka migrations?" — or fifty-page academic CVs. Add it then, for that reason. Not before.

Other things deliberately absent

Not hereWhy not
A retry wrapperThere was one; it made things worse. Both provider SDKs already retry internally, so a second layer multiplied the wait — an exhausted quota took minutes to surface. Retries are now bounded by MAX_RETRIES
A JD "confirm" stepA five-state lifecycle plus versioning that marked old results stale. Ceremony for a demo. A JD is either parsed or it is not
OCR for scanned PDFsNeeds tesseract and poppler as system packages. Such a file fails with a clear message instead
Migrationscreate_all() on startup. Change models.py, delete data/app.db. Right for a demo, wrong for production
AuthNone. Do not expose this to the open internet as it stands

Worked example — capturing "notice period"

  1. Ask for it. Add notice_period_days to LLMScreening in schemas.py, with a description=. That description is the instruction to the model.
  2. Store it. Add the column to Resume in models.py, copy it across in services.screen_resume(), and expose it on ResumeOut.
  3. Show it. Add the field to Candidate in types.ts, then render it wherever you want.
  4. Reset. rm data/app.db and restart — there are no migrations.

Note that you never touched a prompt. That is the point of structured output: the schema is the instruction.
